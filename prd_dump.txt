1. Overview
The Event Booking & Ticketing API lets organizers publish events with a limited number of seats, and lets attendees reserve seats, pay within a limited time and receive tickets. The service is a back-end API only. It also runs background jobs that keep the data correct without manual work, such as releasing seats from unpaid reservations.
2. Problem Statement
Selling a limited number of seats creates two problems. First, when many people try to book the last seats at the same time, the event can be oversold. Second, people who start a booking and never pay keep seats blocked, so other buyers cannot get them even though the seats are effectively free. Organizers need a reliable way to sell seats fairly, and attendees need a simple way to hold a seat while they pay.
3. Goals and Non-Goals
Goals
Never oversell an event, even under concurrent requests
Hold seats for a limited time (15 minutes) and release them automatically if unpaid
Give organizers a simple way to create and publish events
Give attendees a simple way to browse events, reserve seats, pay and view their tickets
Keep the code clean, tested, documented and easy to explain in an interview
Non-Goals (Out of Scope for v1)
A front-end or mobile application
A real payment gateway, refunds or invoices (payment is simulated)
Email or SMS notifications
Seat maps, multiple ticket types or dynamic pricing
Admin role and moderation, password reset, refresh tokens
An organizer cancelling an event with mass cancellation of reservations

7. Non-Functional Requirements
Area
Requirement
Security
Passwords are hashed with BCrypt. JWT authentication with role-based authorization. Error responses never expose stack traces or internal details. The Hangfire dashboard is not publicly accessible in production.
Consistency
Seat changes happen inside a transaction with optimistic concurrency (RowVersion). Two requests for the last seat produce exactly one success.
Performance
Listings use paging, AsNoTracking and DTO projection. Indexes on Event(Status, StartsAt) and Reservation(Status, ExpiresAt).
Reliability
Background jobs are idempotent and log their results. A failed job run is retried by Hangfire.
Maintainability
Clean Architecture with dependencies pointing inward. CQRS with MediatR. Small, well-named classes.
Testability
Handlers depend on interfaces so they can be unit tested. A concurrency test runs against a real database.
Documentation
Swagger for the API and a README with an architecture diagram and a section on how overselling is prevented.

Application, Infrastructure
How overselling is prevented: reserving a seat runs inside a transaction that reads the event, checks AvailableSeats, decreases it and saves. The Event has a RowVersion column. If two requests change the same event at once, the second save fails with a concurrency exception, and the API returns 409 Conflict. The seat count can therefore never go below zero.
